# PassVault Mobile

Flutter (Android + iOS) client for PassVault, talking to the same
`PassVaultapi` backend as `passvault-client` (the Next.js web client). Vault
data is end-to-end encrypted on-device and stored in each user's own Google
Drive -- PassVaultapi only ever proxies opaque encrypted blobs, it never
decrypts them (see `services/vaultData.js`).

## Running it

```
flutter pub get
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:5896
```

`API_BASE_URL` defaults to `http://10.0.2.2:5896` -- `10.0.2.2` is the
Android emulator's alias for the host machine's localhost, matching
`passvault-client`'s default of port `5896`. Override it for a physical
device (use your machine's LAN IP) or a deployed API.

## Local toolchain (this environment)

Flutter SDK and Android SDK are installed outside the repo, not bundled with
it:

- Flutter SDK: `D:\flutter` (added to the user `PATH`)
- Android SDK: `D:\Android\Sdk` (`ANDROID_HOME`/`ANDROID_SDK_ROOT`), with
  `platform-tools`, `platforms;android-36`, and `build-tools;36.0.0`
  installed and licenses accepted

Run `flutter doctor -v` to confirm. iOS builds need a Mac (Xcode) and aren't
possible from this Windows machine -- the iOS-specific code
(`ios/Runner/Info.plist` location permission string, etc.) is in place, but
untested here.

## Why the vault crypto has its own test vector

`lib/core/crypto/vault_crypto.dart` re-implements
`passvault-client`'s `src/lib/vaultCrypto.js` (PBKDF2-HMAC-SHA256, 210,000
iterations -> AES-256-GCM, 12-byte IV prefixed to the ciphertext, all
base64) using PointyCastle instead of WebCrypto. Both clients have to
produce byte-identical output for the same vault password -- a vault
created on the web has to open on mobile, and vice versa. See
`test/crypto/vault_crypto_test.dart`, which hardcodes a vector generated by
Node's WebCrypto (spec-identical to browser WebCrypto) and asserts the Dart
implementation matches it exactly, in both directions.

## Known limitations (MVP scope)

- **Deep linking is not wired up.** The emailed verify-email/reset-password
  links normally open `passvault-client` in a browser; this app has no
  custom URL scheme or App Links configured yet, so `VerifyEmailScreen` and
  `ResetPasswordScreen` ask the user to paste the token from the link
  manually instead of consuming it automatically.
- **Google Sign-In needs real per-project credentials this repo can't
  generate.** `android/app/google-services.json` (from a Firebase/Google
  Cloud project, with your app's SHA-1 signing fingerprint registered) and,
  for iOS, a `REVERSED_CLIENT_ID` URL scheme in `Info.plist`. Until that's
  done, the Google button (shown only when White Label has
  `isGoogleLogin` configured) will fail to sign in.
- **reCAPTCHA is not implemented.** If the resolved White Label has
  `isRecatchEnable` on, `POST /vault/auth/login` will reject with "Please
  complete the reCAPTCHA challenge" -- there's no in-app widget to satisfy
  it yet (would need a WebView bridging Google's JS reCAPTCHA API).
- **Profile, activity log, subscription/package, and account
  suspend/delete are not built yet** -- deferred to a second pass after the
  vault (accounts/notes) screens.

## Structure

- `lib/core/` -- cross-cutting: `api/` (Dio client mirroring
  `passvault-client`'s `src/lib/api.js` envelope-unwrap + Bearer auth),
  `crypto/` (vault key derivation + AES-GCM), `storage/` (secure JWT
  storage), `location/` (mandatory geolocation for login/register/Google
  sign-in, per `requireGeolocation` in `services/vaultAuth.js`), `router/`,
  `theme/`.
- `lib/features/auth/` -- registration, email verification, set/forgot/reset
  password, login, Google sign-in, 2FA (TOTP + mail OTP) setup and
  verification, session state.
- `lib/features/home/` -- placeholder post-login screen (proves the
  auth/session round-trip); the real vault UI (accounts/notes) is next.
